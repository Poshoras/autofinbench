# AutoFinBench-Step3：面向金融 agent 的自动生成 benchmark（2 小时闭环产出）

日期：2026-11-27（05:54–07:54，无人工干预）· 出题：Claude · 答题：Codex（gpt-6-astra，reasoning high）

## 一句话结论

- 产出了 **13 个任务族、26 道题**（25 道可内联运行，1 道工具层），所有 GT 都由程序从环境文件复算，并在作答前做了承诺。
- 在本次能用的求解设置下（环境全部内联、不执行代码、单次作答），**gpt-6-astra 的 pass@1 是 25/25，pass^3 是 24/25**。唯一一次失误是 70 行账本里的 1 美元算术误差。
- 也就是说：**"小型闭合环境 + 程序化 GT"这类金融陷阱题，对最强的模型已经饱和**。要拉开差距，必须进入需要工具、规模和多轮交互的设置（见 §5）。
- 但**对较小的模型仍然有区分度**（§6）。用 3 个模型组成模型集合 ℳ 后，全对数（严格口径）分别是：gpt-6-astra 25/25，gpt-5.6-luna 20/25，gpt-6-luna 19/25。区分度集中在 **F4 规则化记账**和 **F2 静默阻碍 / 压力下的阻碍披露**。

## 2. 数学化定义（对应 `survey/BENCHMARK_DEFINITION.md` §5）

**单题**：τ = (u, E, s₀, Y\*, R, σ\*)
- u：`questions/qNNN.md`。
- E 与 s₀：`env/qNNN/`，以及题干中的 as-of 日期。题干声明这是唯一允许使用的信息源。
- Y\*：`gt/qNNN.json`。数值答案、阻碍标记、标签集合，都由程序计算。
- R：`gen/score.py`。数值容差、集合相等、null 检查，不使用 LLM judge。
- σ\*：oracle 代码（`gen/oracle_xbrl.py`、`gen/gen_ap.py:oracle`），**只读 env 文件**就能复算出 Y\*。

**错误签名**：每道题都预先算好"典型错误会得到的值"，例如违反时点约束、把 YTD 当作单季、混用拆股前后口径、采纳注入内容、采纳越权指令。答案一旦命中某个签名，就能自动归因。

**Benchmark 层**：B = (c, p_T, {τ_i}, Π, Agg, U, Meta)
- c：见 §3 的"能力"列。
- p_T：任务族 × 参数，即生成器。
- Π：本次设置（见 §4）。
- Agg：pass@1、pass^3。
- U：按任务族报告。
- Meta：as-of 日期、修订号、轮次。

## 4. 求解设置与局限（如实说明）

1. **远端 Codex 监控在 06:01–06:41 之间没有任何回应**，`answers/` 一直为空，可能是因为用户的电脑处于离线状态。为了让实验继续，我改用本机 `codex exec`：codex-cli 0.169.0，模型 gpt-6-astra，与用户配置一致。
2. **本机 Codex 的沙箱（bwrap）没有 user namespace 权限，无法启动**，所以它不能执行任何命令。我**没有**用 `--dangerously-bypass-approvals-and-sandbox` 让它无沙箱运行，原因是安全，而且那样它能读到私有 GT 和原始 XBRL 数据。
3. 因此本次的 **Π = 环境文件全部内联进提示词（q024 约 13 万 token），不执行代码，单次作答**。这是"信息完整给出"的设置，偏向测阅读、推理和规则遵循，不测检索和工具使用。
4. 每个答案文件顶部都注明了作答设置。如果远端 Codex 之后带着工具补答，可以直接得到一组**同题不同设置**的配对对照。注意：GT 已在 06:59 公开（`gt/`，commit 491dde8），**这个时间之后提交的答案不应视为有效作答**。
5. 题目数量不多（26 道），属于预实验规模。所有分数都来自同一个求解模型。

## 5. 关于"前沿"的结论与下一步

**证据**
- 有提示 / 无提示孪生题全部答对（q003↔q016，q004↔q015）。
- 行为维度（压力、注入、越权）全部答对。
- 13 万 token 的 haystack 和审核者角色的题也全部答对。

**含义**
- 在信息完整、单次作答的设置下，**这一层的金融陷阱已经不是前沿模型的瓶颈**。
- 这和各大厂的选择方向一致：他们的 agent 评测已经转向需要工具、规模和多轮交互的任务（`survey/LAB_BENCHMARKS_2026-11.md`）。

**下一步：最小改动就能把这套题升级为真正的 agent 题**
1. **工具层**：环境放大到"整个 EDGAR 缓存"或数十万行的账本，只能通过执行代码检索（q026 就是样板，GT 已经算好）。同一套错误签名可以直接复用。
2. **多轮**：用修订号模拟中途改口径或改需求（README 的协议本来就支持"修订后重答"）。
3. **成本维度**：报告 token 和时间消耗。
4. **另换求解器**：例如更小的模型或开源模型。饱和是相对于求解器而言的，AutoBencher 的难度和区分度本来就是相对于模型集合 ℳ 定义的。
